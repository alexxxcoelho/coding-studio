# Coding procedure and its instrumentation

This document describes the coding procedure applied to the interviews of the thesis. The procedure is set out first in terms that any researcher could reproduce with a spreadsheet and a text editor. The second part states how Coding Studio executes each step and what it records. The text is written so that it can be adapted for the methodology chapter and the appendix on the use of artificial intelligence.

## Part one: the procedure

### 1. Corpus and sources

The corpus consists of one folder per interview, identified by a stable code (INT, ECO, RET or ADJ followed by a number) that links the interview to the fieldwork tracker, the preparation file and the analysis. Each folder holds the transcript in one or more forms: the transcript produced by the conferencing platform, the raw output of the speech recognition engine, a cleaned and diarised version, or, for written contributions, the message received. Before any analysis, every file is inventoried and its SHA-256 digest is recorded, so that any later change to a source can be detected.

### 2. Units of analysis

One transcript per interview is designated as the primary source. It is divided into units by a fixed rule that requires no interpretation: one unit for each continuous turn of a speaker, a turn longer than 150 words being divided at sentence boundaries without reordering. Each unit receives an identifier composed of the interview code and a sequential number, together with the speaker, the time mark at which the turn begins and the text. The text is not altered beyond the removal of redundant spaces, so that every quotation can later be found word for word. Lines of the source that are not speaker turns, such as editorial notes on inaudible passages, are listed rather than silently discarded. The list of units is fixed once coding begins.

### 3. Two passes over the units

The Technology, Organisation and Environment framework names three contexts that shape the adoption of an innovation, the technological, the organisational and the environmental, without prescribing a fixed list of factors within them: each study selects the factors that fit its technology and setting (Tornatzky and Fleischer 1990; Baker 2012). The framework is therefore kept as the theoretical frame of the thesis, and the coding works in two passes that use it differently.

The first pass is a provisional pre-classification. The candidate assigns each unit to the technological context (TECH), the organisational context (ORG), the environmental and interorganisational context (ENV), or to CONTEXT when the unit only describes the respondent, the organisation or the scope of the account; a unit that touches several contexts carries each of them, and a unit that is not relevant is marked NA. These assignments orient the reading and decide which units are coded in detail; they remain open to revision throughout the analysis and are not submitted to a second coder.

The second pass codes every unit whose first-pass category is not NA with concrete codes, each naming a mechanism in the respondent's terms, such as a legal obligation, a customer requirement, a lack of skills, or a cost borne by a party that draws no benefit from it. Each code is attached to a TOE context where the attachment is meaningful, and records whether it comes from the literature or from the field. A unit may carry several codes. When no existing code fits, the candidate records a provisional label with a short note rather than forcing a code; the label is later either turned into a new code, defined and marked as coming from the field, or mapped to an existing code, and the decision is applied to every unit that carries the label. Coming from the field is thus a property of a code, not a category set beside the three contexts.

### 4. The candidate's coding

For each unit coded in detail, the candidate may also record a sub-code, a modifier, an evidence level, the provenance of the statement and an analytical memo, and may mark the exact words that will serve as a quotation. Interview summaries and record sheets may be consulted during this step; they are never given to the secondary coder. The codebook evolves as interviews are coded: definitions are refined, codes that prove to name the same mechanism are merged, and the passages already coded with a code are revisited when its definition changes. Each such change is dated and kept.

### 5. A language model as a challenger

The concrete codes, and only they, are submitted to a language model acting as a blind second reader. The model receives the codes offered (code, label and definition, grouped by TOE context), the rules of the task and the units, and nothing else: neither the candidate's codes, nor the first-pass categories, nor the provisional labels, nor memos, summaries or material from other interviews. The rules are those of protocol P-04: use only the codes listed, answer NA when no code applies, code what is said in the unit rather than what may be inferred from the interview, treat the interviewer's turns as NA unless they report a fact from the field, write no commentary, and process every unit in order. The answer must be a single JSON object in a prescribed structure, which names the interview and the version of the units it refers to. Long interviews are divided into parts, each answered separately; the parts generated together form a batch, and each run of the model answers one batch.

The candidate's reading is formed before the model's is seen, and it is fixed at the moment it leaves: a prompt can only be generated once every unit of the batch carries the candidate's coding (codes, or a provisional label, which counts as an empty coding), and the generation of the prompt freezes a copy of that coding, with the versions of the units and of the codebook it refers to, as the reference of every comparison with the answers to that batch. This reference is never edited; it is the frozen reading, not the coding at the time the answer is read, that the model's answer is compared with, because with a copy-and-paste workflow the answer may have been read before it is imported. An answer is accepted only for a batch whose reference exists and covers every unit of the part it answers. It is kept exactly as returned and is accepted only if it refers to the right interview and version of the units, covers every unit of its part exactly once, and uses only the codes offered in that batch or NA. An answer that fails any of these checks is rejected as a whole, and every problem found is reported. For each run the model name and version, temperature, seed, context length, batch size, prompt version and time of execution are recorded.

### 6. Review

The comparison serves the interpretation, not a target figure. Three objects are kept apart: the initial comparison, between the frozen reference and the model's answer; the candidate's revisions, made at any time after the prompt was generated; and the final decision. Every unit on which the frozen reference differs from the model is reviewed, together with a sample of the units on which they agree: at least five agreeing units or a tenth of them, whichever is larger, drawn on the frozen reference by a deterministic procedure whose seed is recorded, so that agreement is examined as well as disagreement. A later revision of the candidate's coding never removes a unit from the review nor changes the sample: the unit is shown with its frozen coding and its current one, and marked as revised. For each reviewed unit the candidate keeps the frozen coding, adopts the model's codes or settles on a different set of codes, and gives a written rationale for every disagreement. The candidate keeps the final decision; a decision may be revised, and earlier decisions remain on record. When a unit is covered by runs answering different batches, the reference shown is the one of the latest batch, and each run is also listed with the reference it was compared with.

The share of units with identical codes and Cohen's kappa per code, computed between the frozen reference and each run on the presence or absence of each code, are reported for transparency, without any model in the calculation; kappa is reported as undefined when only one level is observed for a code. The final coding of a unit is the review decision where one exists, and the candidate's coding otherwise.

### 6a. Claims: the unit of evidence qualification

A unit may carry several statements that do not share the same standing. The qualifications of evidence are therefore attached to the statement, not to the unit: the candidate marks an exact passage of the unit, the claim, and gives it an evidence level (EV0 to EV4), a provenance (spontaneous, probed, derived from a document, inferred by the researcher) and a role in the decision described (trigger, retrospective justification, enabling condition, constraint, or undetermined), together with the codes of the unit it supports. A claim may support several codes without counting as several pieces of evidence; distributions of evidence levels, provenances and roles count distinct claims, and the counting unit is stated wherever a figure is given. A story told after the event is not a retrospective justification by default: the role is assigned only when the justification is identifiable in the passage. Roles distinguish positions in the decision; they do not measure a causal weight. Claims are revisited when the codes of their unit change or when the text of the unit is corrected.

### 6b. Verification against the recording

The transcript is checked against the recording for every unit that carries a quotation or a claim, every unit flagged as uncertain, every disagreement with the model, every unit attributed to a case, and a sample of the remaining units of at least five or a tenth of them, drawn by a deterministic procedure whose seed is recorded. Each unit is in one of three states: unverified, verified, or unusable. A correction of the text or of the speaker never rewrites the segmentation: it is recorded as a dated overlay with its reason, the original is kept, and the unit returns to the unverified state until it is checked again. Four flags qualify a unit at any time: uncertain attribution or wording, second-hand account, unfinished sentence, and co-constructed content, the last one distinguishing a mere assent to the interviewer's wording from an answer with content of its own. Counts describe the eligible coded corpus; the coverage of the verification is reported next to them, separately. A unit whose text or speaker remains uncertain supports no conclusion until the uncertainty is resolved.

### 7. Synthesis by case

The material is then summarised by case, a case being one identifiable decision about item-level identification: adopted, deferred or rejected. A case is documented by the units the candidate attributes to it, which may come from several interviews when several respondents speak of the same project; a case to which no unit has been attributed is marked as undocumented and contributes nothing to the comparison, so that general remarks or another project's units are never counted for it by default. For each case the candidate records the decision, the granularity of identification (item, batch or model), the carrier chosen and the carriers rejected, the kind of account (first hand, reported, ecosystem view or anticipation), the link to Switzerland, the stage reached and the outcome status in the terms of the codebook, and then the trigger of the project, the alternatives considered, the constraints met, the choice made and its result. For each of these five fields the candidate writes what the data support, what contradicts it and what is missing, and selects the excerpts that illustrate it from the attributed units. The cases are then compared question by question: each code is mapped to the research questions it bears on, and for each question the codes found among the attributed units of each case are set side by side with the units that carry them. The comparison is used to answer the research questions, not to count how often each context appears.

### 7a. Answers by question and the saturation record

For each research question the candidate keeps a memo in four separate parts: what the data document, the interpretation, the competing explanations, and the limits, each part pointing to the units that support or contradict it. The answers of the thesis are written from these memos, never derived from frequencies. A saturation record lists, in the order in which the interviews were coded, the codes used for the first time and the codes created from the field; the enrichment of the meaning of a code is documented in memos and is not computed. The record is provisional, and a stop decided by recruitment or by the calendar is named as such.

### 8. Audit trail

Every step above is recorded as it happens: inventory of sources, choice of the primary source, segmentation, each coding decision with its pass and its previous and new value, each label and its resolution, each change to the codebook, each prompt and the frozen reference taken with it, each run and each answer, each agreement sample, each review decision, each case with its attributed units, each claim, each flag, each correction, each verification, each memo, and each export. The record can be extended but never edited. Each entry contains the digest of the preceding one, so that any later alteration of the record becomes detectable. For each interview, an archive gathers the units, both passes of the candidate's coding, every prompt and the frozen reference of each batch, every answer, the agreement report, the review log with the revisions made since each reference, the final coding, the labels and their resolution, the case syntheses with their attributed units, the claims and their distributions, the verification states and corrections, the codebook, the relevant part of the record, a digest of the whole state the package was produced from with the version of the program, a copy of the database, and a manifest of the digests of all these files. A package is never modified; the empirical tables of the final manuscript come from a single package.

## Part two: execution by Coding Studio

Coding Studio is a program written for this thesis that executes the procedure above on the candidate's computer. It runs locally, makes no network call and never calls a language model itself: the candidate copies each prompt into the chosen model's interface and pastes the answer back. The source code is kept with the thesis tools in `00_Tools/CodingStudio`.

### Sources and units

The library is built by scanning the interview folder. For each file the program records its type, size, modification time and SHA-256 digest; archive folders, scripts, media and attachments are excluded from the inventory and listed as such. On every subsequent scan, only additions, removals and changes of digest are recorded. Readers are provided for the formats found in the corpus: WebVTT from the conferencing platform, timestamped text from the speech recognition engine, cleaned transcripts in Markdown with interviewer and respondent labels, exports of the Budgie Echo transcription tool and written responses. The segmentation rule is the one of `00_Tools/Scripts/segment_transcript.py`; the list of units is stored with the digest of the source and its own digest, and a new segmentation is refused once any coding exists.

### Coding

The candidate codes in a two-pane interface: the units on the left, the selected unit and the code picker on the right. In the first pass a single key assigns a category and moves to the next unit. In the second pass the picker offers every active code, those attached to the unit's first-pass contexts first, and a provisional label can be put on the unit at any time. The program refuses codes that are unknown, inactive or merged, NA combined with another code, and quotations that are not an exact substring of the unit. The codebook is first read from the thesis coding database, which the program opens in read-only mode, and then maintained in the program: codes can be created, edited, merged into another code or deactivated, each change incrementing the version of the code, and the codebook can be exported as files in the format of the thesis database. For any code, the program lists every unit that carries it, so that passages can be revisited after a change of definition.

### Prompts and answers

The prompt is generated from the units in scope and the codes offered to the model, in English, and is identical for identical inputs. It carries the identifiers of the interview, of the version of the units and of the codes offered, so that each answer can be matched to the material it was produced from. The program refuses to generate a batch while any unit of it lacks the candidate's phase 2 coding, and writes, in the same transaction as the prompts, the frozen reference of the batch: the candidate's coding of each unit, the digests of the units and of the codebook, and the digest of the reference itself. Every generated prompt is stored with its digest, its batch and the list of codes it offered. Before an answer is accepted, the program checks that the candidate has coded every unit of its part; it then keeps the pasted text and its digest, extracts the JSON object, and applies the checks described in step 5 against the batch the run answers, so that a later change to the codebook does not invalidate an answer to an earlier prompt.

### Review, cases and export

When a run becomes complete, the program draws its sample of agreeing units on the frozen reference of the run's batch, stores it with its seed and records it. The review presents each disagreement, then each sampled unit, with the frozen codes, the current codes when they differ, and each run's codes side by side; a disagreement cannot be decided without a rationale. The agreement measures are computed between the frozen reference and each run with the formulas of `00_Tools/Scripts/compute_agreement.py`. Cases carry their descriptive fields, their five synthesis fields with what supports, contradicts and is missing, and the units attributed to them from any interview; an excerpt can only illustrate a field once its unit is attributed to the case. The cross-case view arranges, for each research question, the codes found among the attributed units of each case, and marks the cases without attributed units as undocumented. The export writes the archive described in step 8 to a new dated folder, never overwriting an earlier one, with CSV files in the formats of the thesis scripts so that the results can be recomputed independently of the program.

### Claims, verification and memos

Claims are entered on the unit, the excerpt being selected in the unit text and checked as an exact substring; the closed lists of evidence levels, provenances and roles are enforced, and the codes of a claim must belong to the unit's current coding. Flags and corrections are entered on the unit; the program computes the verification state from the latest verification and the current text, so that a correction makes a verified unit unverified again. The list of units to verify and the coverage figures are computed on request, the sample of the remaining units being drawn once with a recorded seed. The memos by research question are edited in the program and exported as the answers file; the saturation record is computed from the audit log and the current coding. The prompt sent to the model redacts any unit identifier found in the texts of the codebook, so that the origin of a field code cannot reveal the candidate's coding of the units being challenged.

### Integrity of the record

The record is a table of the program's database in which each entry stores the SHA-256 digest of its own content and of the preceding entry. Database triggers refuse any modification or deletion of the record, of the stored prompts, of the frozen references, of the stored answers, of the agreement samples, of the review decisions and of the resolutions of labels. The program recomputes the whole chain on request and reports the first entry that does not match. Each change to the coding and its entry in the record are written in a single transaction, so that neither can exist without the other.

### Limits

The program enforces the order of operations it controls: the candidate codes every unit of a batch before its prompt can leave, the reference is frozen at that moment, and later revisions are shown next to it rather than hidden. It cannot prevent a researcher from consulting a model outside the program. The candidate's coding remains a human judgement that the program records but does not assess. The digest chain detects alterations of the record; it does not prevent someone with access to the files from replacing the whole database, which is why the exported archives, with their manifests, are kept with the thesis materials.
