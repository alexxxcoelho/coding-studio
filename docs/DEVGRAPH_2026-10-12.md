## Contracts (decided by the orchestrator, applied by every task)

### C1. Cases documented by several interviews, no automatic attribution

- New table `case_units (case_id TEXT NOT NULL REFERENCES cases(case_id), unit_id TEXT NOT NULL, interview_id TEXT NOT NULL REFERENCES interviews(interview_id), PRIMARY KEY (case_id, unit_id))`: the units attributed to the case. A unit may belong to any interview; it must exist in the current segmentation of its interview.
- `Case` (cs-model) gains: `units: Vec<String>` (attributed unit ids, sorted, deduplicated), `interviews: Vec<String>` (read-only, derived from `units` plus `interview_id`, sorted), `decision: Option<String>` (`adopted` | `deferred` | `rejected` | other free text), `granularity: Option<String>` (`item` | `batch` | `model` | other), `carrier_chosen: Option<String>`, `carriers_rejected: Vec<String>`, `account_type: Option<String>` (`first-hand` | `reported` | `ecosystem` | `anticipation` | other), `swiss_link: Option<String>`. All `#[serde(default)]`.
- `CaseField` gains `contradictions: String` and `missing: String` (`#[serde(default)]`), next to `text` (what the data support) and `evidence` (illustrative unit ids).
- Rule: every `evidence` unit of every field must be in `units` (an excerpt that illustrates the synthesis is first attributed to the case). Validation error otherwise, naming the field and the unit.
- Rule: `cross_case()` uses only `units`. A case with no attributed unit gets, for each research question, a cell with `documented: false` and no codes. `CrossCaseCell` gains `documented: bool`. The final phase 2 coding of each interview that holds attributed units is used.
- `cases.interview_id` stays the interview the case was created from (id generation `<ID>-C<n>`, listing by interview). `GET /api/cases` lists all cases; `GET /api/interviews/{id}/cases` lists the cases whose `interview_id` is the interview or whose `interviews` contains it.
- Audit: `case.create` / `case.update` events carry before and after including `units`.
- Export (`cs-app/export.rs`): `cases.json` and `cases.md` include the new fields; new `cases.csv` with one row per case: `case_id,label,interview_id,interviews,decision,granularity,carrier_chosen,carriers_rejected,account_type,swiss_link,stage,outcome_status,n_units` (lists joined with `;`); new `case_units.csv`: `case_id,unit_id,interview_id`.

### C2. Immutable human reference, taken when the challenger package is generated

- New table `human_snapshots (snapshot_id INTEGER PRIMARY KEY AUTOINCREMENT, interview_id TEXT NOT NULL REFERENCES interviews(interview_id), batch_id INTEGER NOT NULL, phase INTEGER NOT NULL, segmentation_hash TEXT NOT NULL, codebook_hash TEXT NOT NULL, codings TEXT NOT NULL /* JSON object unit_id -> sorted codes array, for every unit of the batch */, sha256 TEXT NOT NULL /* of codings */, created_at TEXT NOT NULL, UNIQUE (interview_id, batch_id))`, with `_no_update` and `_no_delete` triggers like `prompts`.
- `Store::record_prompts` takes the snapshot in the same transaction as the prompts: it refuses (Validation error listing the unit ids) to generate a batch while any unit of the batch lacks a phase 2 human coding (codes or an open label to clarify; a unit with only an open label is stored with an empty codes array). The snapshot event `human_snapshot.take` is appended with `batch_id`, `sha256`, `n_units`.
- The import guard in `record_ai_output` stays (every unit of the part coded), unchanged.
- `Store::human_snapshot(interview_id, batch_id) -> Result<HumanSnapshot>` (cs-model: `HumanSnapshot { snapshot_id, interview_id, batch_id, phase, segmentation_hash, codebook_hash, codings: CodingMap, sha256, created_at }`).
- `Store::review`: the human reference of a run is the snapshot of the run's batch. Disagreements are computed between the snapshot and the run; the agreement sample is drawn on the snapshot. `ReviewItem` gains `human_current: CodeSet` (the candidate's current coding of the unit) and `revised_since_snapshot: bool` (`human != human_current`); `human` is the snapshot value. `Review` gains `snapshots: Vec<(run_label, snapshot_id, sha256)>`.
- `Store::final_codings` unchanged: decision where one exists, otherwise the current human coding.
- Agreement report (`cs-ai` report / `Store::agreement` route) computed on the snapshot, not on the current coding.
- Export: new `human_snapshot_batch<id>.csv` (`unit_id,codes`) and `review.md` states, per unit, snapshot codes, current codes, run codes, decision.
