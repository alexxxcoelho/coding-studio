# Préparer l'étude {#preparer}

## Pourquoi cette étape {#preparer-pourquoi}

Une analyse qualitative se défend par sa traçabilité, et la traçabilité se décide avant le premier codage. Il s'agit de dire ce que vous cherchez (les questions de recherche), qui vous avez interrogé (les attributs d'entretien) et comment vous allez lire (les modèles de mémo, la liste de contrôle). Braun et Clarke (2006, 2021) rappellent que l'analyse thématique n'est pas une technique neutre : les choix du chercheur la façonnent, et ils doivent être explicites. Noter dès le départ le statut des propos (déploiement vécu, projet non réalisé, avis d'expert) évite de donner plus tard le même poids à des situations différentes. Cette étape se fait une fois par étude.

## Ce que vous faites {#preparer-actions}

### 1. Créer le projet {#preparer-projet}

Un projet correspond à une base de données et à un dossier de transcriptions. Tout ce que vous faites ensuite (codes, mémos, thèmes, journal) est écrit dans cette base.

**Dans Coding Studio.** Au premier lancement de l'application de bureau, une fenêtre demande où garder la base : choisissez un dossier que vous sauvegardez. Depuis un terminal, vous désignez la base et le dossier des entretiens par les options de lancement. Pour changer d'étude, ouvrez ou créez une autre base depuis le menu Base de données. Rien ne quitte votre machine tant que vous ne configurez pas de fournisseur d'IA.

### 2. Ouvrir les Réglages {#preparer-reglages}

Les Réglages sont l'écran où se définit l'étude. On y vient au début, puis rarement.

**Dans Coding Studio.** Cliquez sur Réglages dans la barre du haut. Le bloc Étude contient le nom de l'étude, une description d'un paragraphe (lue par le modèle si vous lancez une revue IA), les questions de recherche, les règles de codage, la longueur maximale d'une unité (150 mots par défaut), les noms des intervieweurs et les préfixes d'identifiants. Enregistrer valide le bloc, et chaque modification est datée dans le journal. Les autres blocs sont Fournisseurs IA (facultatif), Exports et vérification, et Modèles et listes de l'étude, où se trouvent les attributs, les modèles de mémo, le cadre d'interprétation, les dimensions personnalisées de la matrice et les listes éditables. Exemple de règle de codage : « Coder ce que le répondant affirme ; plusieurs codes possibles ; marquer non pertinent si rien d'utile. »

### 3. Écrire les questions de recherche {#preparer-questions}

Vos questions orientent la lecture. Elles servent à relier les codes aux thèmes, puis les thèmes aux réponses finales.

**Dans Coding Studio.** Dans Réglages, bloc Étude, champ Questions de recherche, saisissez une question par ligne, chacune avec un identifiant court (Q1, Q2, ...), repris dans la fiche de thème, dans Rédiger et dans les exports. Exemple fictif : Q1, pourquoi une petite bibliothèque change-t-elle de système de prêt ? Q2, qu'est-ce qui rend le changement difficile ? Q3, quel rôle joue le réseau de bibliothèques ? Un texte reformulé reste historisé dans le journal.

### 4. Définir les attributs d'entretien {#preparer-attributs}

Un attribut est une caractéristique de l'entretien que vous voudrez utiliser plus tard comme filtre ou comme ligne de matrice. Il se définit une fois pour le projet et se remplit pour chaque entretien.

**Dans Coding Studio.** Dans Réglages, bloc Modèles et listes de l'étude, section Attributs d'entretien, cliquez sur + Attribut, donnez un nom et un type : texte, liste de valeurs, nombre ou date. Exemples : type de bibliothèque (liste : communale, scolaire, associative), rôle du répondant (texte), nombre de bénévoles (nombre), date de l'entretien (date), version du guide d'entretien (liste : A, B), statut des propos (liste : expérience vécue, projet, avis d'expert, observation indirecte). Les attributs deviennent des colonnes de la Bibliothèque, des filtres et des lignes ou colonnes de la matrice. Le statut des propos est fortement recommandé. Les valeurs se remplissent dans la fiche de chaque entretien (action 10). La même section propose des dimensions personnalisées de la matrice (+ Dimension), par exemple « qui décide, qui paie, qui utilise ».

### 5. Préparer les modèles de mémo {#preparer-memos}

Le mémo de familiarisation se rédige après la lecture complète d'un entretien et avant tout codage. Ses questions dépendent de votre étude, donc elles se règlent dans un modèle.

**Dans Coding Studio.** Dans Réglages, bloc Modèles et listes de l'étude, section Modèles de mémo de familiarisation, cliquez sur + Modèle, donnez-lui un nom, puis saisissez les questions. Vous pouvez avoir plusieurs modèles (par exemple « Par défaut », 4 questions, et « Entretien expert », 6 questions) et en marquer un par défaut. Dans la fiche d'un entretien, vous choisissez le modèle ; dans l'écran Coder, vous ajoutez, retirez ou reformulez une question pour cet entretien seul, sans toucher au modèle.

Un modèle générique par défaut :

1. Que raconte ce répondant, en quelques lignes ?
2. Qu'est-ce qui m'a surpris ?
3. Quelles contradictions ou particularités relève-t-on ?
4. Que faudrait-il demander aux entretiens suivants ?

Un second exemple, pour une étude d'un autre type (l'expérience de patients après une sortie d'hôpital) :

1. Quel est le parcours décrit, du premier symptôme à aujourd'hui ?
2. Qui a aidé, et qui a manqué ?
3. Quels mots le répondant emploie-t-il pour parler de sa situation ?
4. Quel point faut-il vérifier à l'oreille avant de le citer ?

### 6. Régler la liste de contrôle de fin d'entretien {#preparer-checklist}

La liste de contrôle est une série de cases à cocher que vous passez en revue à la fin du codage d'un entretien. Elle vous évite d'oublier un passage de vérification.

**Dans Coding Studio.** Dans Réglages, bloc Modèles et listes de l'étude, section Listes éditables, la liste Fin d'entretien compte quatre points par défaut : tous les tours du répondant vus ; codes Plus tard traités ou assumés ; mémos des nouveaux codes écrits ; mémo de fin d'entretien rédigé (position du répondant, mécanisme central, exceptions, questions pour les suivants). Ajoutez, retirez ou reformulez. Elle s'affiche dans le panneau Fin d'entretien de l'écran Coder (voir [Coder](02_coder.md#coder-checklist)). Les autres listes éditables sont les contrôles d'un thème (7), les natures de preuve (5) et les types de lien (6).

### 7. Choisir un cadre d'interprétation, ou aucun {#preparer-cadre}

Un cadre d'interprétation est une grille théorique qui sert à lire vos thèmes une fois construits. Il est facultatif. Dans l'approche hybride de Fereday et Muir-Cochrane (2006), le codage reste ouvert aux données et le cadre aide ensuite à interpréter. L'outil suit cette logique : le cadre n'apparaît qu'aux étapes Analyser et Rédiger, jamais dans le codage ni dans le codebook.

**Dans Coding Studio.** Dans Réglages, bloc Modèles et listes de l'étude, section Cadre d'interprétation (facultatif), choisissez Aucun (valeur par défaut), un préréglage (TOE : technologie, organisation, environnement ; TAM/UTAUT) ou Personnalisé, où vous nommez vos propres dimensions. L'outil ajoute toujours une ligne « hors cadre » pour ce que le cadre n'explique pas. Avec Aucun, les champs de lecture par le cadre n'apparaissent pas.

### 8. Déclarer les intervieweurs {#preparer-intervieweurs}

Les tours de l'intervieweur donnent le contexte, mais ne se codent pas. L'outil doit donc savoir lesquels ils sont.

**Dans Coding Studio.** Dans Réglages, bloc Étude, champ Noms des intervieweurs, saisissez les noms ou étiquettes tels qu'ils figurent dans vos transcriptions (par exemple INT). Les tours correspondants s'affichent en gris dans l'écran Coder et ne sont jamais des cibles de codage. Une question peut être fournie au modèle comme contexte du tour du répondant ; elle ne constitue pas une preuve du répondant. Relisez le prompt et sa pseudonymisation avant tout envoi.

### 9. Importer les transcriptions et lire la Bibliothèque {#preparer-bibliotheque}

Importez des transcriptions déjà épurées : locuteurs identifiés, repères de temps, noms pseudonymisés si vos engagements l'exigent.

**Dans Coding Studio.** Placez chaque entretien dans un sous-dossier du dossier des entretiens, nommé avec le préfixe réglé dans l'étude (BIB-01, BIB-02), avec une transcription épurée, un tour par paragraphe, du type `**INT [00:25]:** question` puis `**RESP [00:29]:** réponse` (un exemple fictif se trouve dans `examples/library`). Dans la Bibliothèque, cliquez sur Importer des transcriptions. Chaque entretien devient une ligne, avec les colonnes ID, les attributs de l'étude, Guide, Mémo (fait ou à faire), Coder (par exemple 40 / 97 tours) et Revoir. Le filtre au-dessus de la liste restreint les lignes selon un attribut (par exemple version du guide : B). Un entretien nouveau est découpé en unités, un tour de parole chacune, coupé à la longueur maximale réglée ; le découpage est déterministe. L'empreinte de chaque fichier source est calculée pour détecter toute modification.

### 10. Remplir la fiche d'entretien {#preparer-fiche}

La fiche réunit ce que vous savez de l'entretien avant de le coder.

**Dans Coding Studio.** Dans la Bibliothèque, un clic sur une ligne ouvre la Fiche à droite ; un double-clic, ou le bouton Coder de la fiche, ouvre l'écran Coder. La fiche contient trois blocs. Attributs : les champs que vous avez définis (les listes sont des menus), à remplir avant de coder car ils servent ensuite de filtres dans l'Analyser. Mémo de familiarisation : le choix du modèle de mémo, avec le décompte des questions ajoutées ou retirées pour cet entretien. Source : le fichier de transcription, le nombre de tours et la mention des tours de l'intervieweur, grisés et jamais codés (par exemple 84 tours dont 61 du répondant, 23 grisés).

### 11. Anonymiser localement avant toute revue IA {#preparer-pseudo}

Dans **Paramètres de l’étude → Anonymiser**, choisissez un entretien. Comparez l’original local et la copie, tour par tour. Les noms connus du registre et les règles existantes sont repris. Ajoutez les personnes mentionnées et leurs différentes formes ; réutilisez le même label seulement si vous avez établi qu’il s’agit de la même personne. Examinez aussi les noms dans les locuteurs.

- Le repérage par majuscules propose des mots à examiner, sans IA. Il manque des noms et propose aussi des mots ordinaires.
- Le texte hors des remplacements est conservé : hésitations, répétitions, ponctuation, espaces et erreurs. Le plan de remplacement garde les positions source, y compris en Unicode.
- Une protection séparée masque les emails, numéros internationaux et URL ; ajoutez manuellement les autres coordonnées, adresses et détails identifiants. Les organisations restent telles quelles sauf règle de confidentialité explicite, notamment celles déjà définies dans le projet.
- Relisez toute la copie puis validez-la. Toute modification du texte ou des règles annule cette validation. L’outil ne certifie pas une anonymisation automatique complète.
- **Exporter la copie anonymisée** produit le texte segmenté, le JSON par unités et un manifeste. Les originaux et le codage restent intacts. La table des identités reste dans la base locale et n’est jamais jointe à cet export.

Le prompt de référence amélioré est consultable dans ce même écran. Il est destiné à un environnement local de confiance : n’envoyez pas l’original ou la table à un service IA pour les anonymiser. Les sauvegardes complètes du projet contiennent toujours les données privées et ne sont pas des exports pour correcteurs.

### 12. Exporter ou importer un modèle de projet {#preparer-modele}

Un modèle de projet réutilise vos choix pour une nouvelle étude, sans les données.

**Dans Coding Studio.** Dans Réglages, bloc Modèles et listes de l'étude, Exporter écrit un fichier JSON avec description, questions, règles, cadre, attributs, modèles de mémo, listes éditables et dimensions de matrice. Il ne contient ni transcription, ni codage, ni mémo rédigé. Dans une nouvelle base, Importer un modèle de projet (JSON) remplit ces champs : relisez-les avant de commencer.

### 13. Ajouter un entretien à un corpus déjà analysé {#preparer-ajouter}

Un nouvel entretien prolonge l'étude. Le codebook courant sert de point de départ, sans imposer aux nouveaux propos les conclusions existantes. Il n'est pas nécessaire de recoder tout le corpus.

1. Sauvegardez le projet avant l'import. Dans Bibliothèque, utilisez Importer des transcriptions, puis vérifiez la source, les locuteurs, les repères, la segmentation et les attributs. Ne remplacez pas les sources des entretiens déjà codés.
2. Lisez l'entretien entier et rédigez le mémo de familiarisation avant le premier codage. Distinguez récit vécu, observation rapportée, attente et hypothèse. Les questions de l'intervieweur donnent le contexte, jamais une preuve du répondant par elles-mêmes.
3. Codez les passages exacts avec le codebook courant. Pour une thèse en anglais, conservez les noms et définitions des codes en anglais, et les verbatims dans leur langue originale. Réutilisez un code commun pour un même phénomène, indépendamment du secteur ou du locuteur. Ajoutez séparément chaque dimension effectivement exprimée : « Stock visibility » décrit le phénomène ; « Stated business value » s'ajoute uniquement si le répondant le présente comme une valeur métier. Un passage peut porter les deux. Ne les fusionnez pas dans un intitulé composite.
4. Examinez tous les tours du répondant. Marquez explicitement NA les passages hors périmètre ; laissez une incertitude à revoir plutôt que d'inventer un code. Affinez les premières sélections en fin de séance : limites du passage, codes indépendants, définition, critères d'inclusion et d'exclusion, mémo et citation d'exemple.
5. Créez ou scindez un code seulement si une distinction utile n'est pas couverte. Documentez la raison et la version du codebook. Utilisez Lexique, recherche en contexte et passages proches pour retrouver les occurrences possibles dans les anciens entretiens, puis relisez-les avec leur contexte. Corrigez seulement les passages concernés et clôturez leur harmonisation ; un résultat de recherche ne suffit pas à appliquer un code.
6. La revue IA reste facultative. Si vous la lancez, conservez le codebook et la lecture de référence figés, le prompt, la réponse réelle et les décisions. Arbitrez les désaccords, contrôlez les accords échantillonnés et traitez les concepts proposés. Une ancienne passe ne couvre pas automatiquement les nouveaux passages ou un codebook révisé. Une construction assistée par IA n'est pas une validation humaine indépendante et doit être déclarée comme telle.
7. Contrôlez que les codes finaux décidés se retrouvent bien sur les passages exacts utilisés dans l'analyse. Une décision d'arbitrage enregistrée ne remplace pas ce contrôle des surlignages. Terminez la liste de contrôle, le mémo et les éléments à revoir. Vérifiez à l'audio les citations destinées à la thèse et les passages incertains pour lesquels un enregistrement existe ; ne confondez pas disponibilité de l'audio et réécoute effectuée.
8. Actualisez les thèmes, leurs contre-exemples, les cellules de matrice commentées et leurs liens de preuve, les cas et la synthèse par question. Recalculez les explorations lexicales et les fréquences par attribut ; la fréquence n'est pas l'importance analytique. Révisez le texte de Rédiger avant de régénérer les exports datés et le rapport d'analyse. Le rapport reprend les textes et preuves enregistrés ; il n'atteste pas à lui seul leur validation.

**Lire l'avancement.** Le compteur de codage mesure les tours examinés, codés ou explicitement hors périmètre, sur les tours du répondant. « Plus tard », les marques à revoir, les harmonisations et les décisions ouvertes restent du travail à faire. La revue IA affiche sa propre couverture et peut rester absente ou partielle sans annuler un codage terminé. Le compteur d'arbitrage inclut les désaccords et les accords échantillonnés, au numérateur comme au dénominateur. « Prêt » décrit un état de travail dans l'outil, pas une certification de réécoute ou une validation scientifique indépendante.

## Pièges fréquents {#preparer-pieges}

- Écrire des questions trop larges pour guider la lecture. Une question à laquelle on répond par « tout » n'oriente rien.
- Oublier le statut des propos, puis comparer comme équivalents un déploiement vécu et un avis d'expert.
- Croire que la liste de pseudonymisation suffit. Elle ne rattrape pas une transcription mal anonymisée.

## Ce qui sort de cette étape {#preparer-sortie}

- Un projet avec sa base, ses questions et ses règles de codage.
- Des attributs définis, des modèles de mémo et une liste de contrôle propres à l'étude.
- Un cadre d'interprétation choisi ou, le plus souvent, aucun.
- Les entretiens listés dans la Bibliothèque, découpés en unités, avec une fiche remplie.
- Une liste de pseudonymisation prête.
- Si vous le souhaitez, un modèle de projet JSON réutilisable.

### Ouvrir deux projets à la fois

Dans **Fichier → Ouvrir un projet dans une nouvelle fenêtre…**, choisissez une autre base SQLite. Le premier projet reste ouvert. Chaque fenêtre utilise son propre serveur local, sa base, ses réglages d’étude et son dossier d’entretiens. Le menu **Fenêtre** permet de les retrouver ; le titre indique le chemin de la base. Ouvrir une base déjà affichée ramène à sa fenêtre au lieu d’ouvrir une seconde connexion. Les actions de menu concernent la fenêtre active.

### Préparer un entretien à l’import avec une IA locale

1. Dans **Paramètres de l’étude → Préparation des transcriptions**, indiquez l’URL locale et le modèle. **Tester et lister les modèles** ne transmet aucune transcription. Exemple : `http://127.0.0.1:1234` pour LM Studio (le suffixe `/v1` est ajouté si nécessaire).
2. Activez les opérations voulues : **anonymiser**, **nettoyer légèrement**, **traduire vers** une langue de votre choix. Laissez la langue vide pour conserver celle du fichier. L’anonymisation est distincte du nettoyage : sa copie fidèle conserve les hésitations et erreurs.
3. Dans **Importer des transcriptions**, cochez la préparation locale puis choisissez les entretiens. Seuls les nouveaux sont présélectionnés ; les entretiens déjà codés, surlignés ou envoyés en revue IA reçoivent une copie de consultation, sans remplacer leur texte codé.
4. Lancez la préparation. Le texte original part uniquement vers l’adresse locale ou l’IP privée explicitement choisie. Utilisez un serveur de confiance dont vous maîtrisez le fonctionnement : Coding Studio ne peut pas vérifier si ce serveur relaie lui-même les requêtes. L’application ne suit aucune redirection, n’utilise aucun proxy et ne bascule pas vers un service hébergé. L’avancement montre les groupes de tours ; **Arrêter** empêche l’envoi des groupes suivants (la requête en cours peut finir).
5. Comparez tous les tours et les correspondances d’identités. Choisissez la **copie fidèle** ou la **version nettoyée / traduite**. Les tours, locuteurs, repères de temps et identifiants restent structurés. Les changements de nombres ou de labels, les tours supprimés et les réponses tronquées sont refusés. Ces contrôles ne garantissent pas la fidélité sémantique : vérifiez négations, conditions, incertitudes, répétitions significatives et termes techniques.
6. Validez explicitement la version choisie pour le codage, ou rejetez-la. Avant validation, seule une proposition privée est enregistrée ; les sources et le codage ne changent pas. La source originale, l’ancienne segmentation et les corrections antérieures restent conservées après validation. Une proposition non validée peut être reprise à la réouverture du parcours. La revue IA de phase 2 conserve ses propres contrôles de confidentialité et de prompt.

Une transcription nettoyée ou traduite est une version dérivée, même après relecture. Les exports indiquent le modèle local, les opérations demandées et la version choisie ; ne présentez pas une traduction comme un verbatim dans la langue originale.

**Contexte et thinking du modèle local.** Indiquez la fenêtre effectivement chargée dans votre serveur (par exemple 131072 tokens). L’anonymisation privilégie l’entretien entier : seuls les noms sont retournés, puis les remplacements sont appliqués localement. Le découpage intervient si le budget estimé dépasse ce contexte ; une marge couvre les instructions, le dictionnaire et la réponse. Pour le nettoyage et la traduction, la réponse doit répéter le texte : leur découpage dépend aussi de la limite de sortie, indépendamment de la grande fenêtre d’entrée. Le compteur porte sur ces requêtes, plus sur des groupes fixes de six tours. Avec une API compatible OpenAI, Thinking peut être désactivé (`reasoning_effort: none`) ou activé avec un effort choisi (`minimal`, `low`, `medium`, `high`, `xhigh`, `max`). Le choix « réglage du serveur » ne force aucun effort. Le serveur et le modèle doivent accepter les réglages choisis. Désactiver le thinking ne garantit pas l’exhaustivité de la détection : relisez toujours les noms et les rapprochements d’identités.

### Préparer depuis la bibliothèque, importer les intervenants et partager les originaux

- Dans **Bibliothèque → Anonymiser / nettoyer / traduire…**, choisissez les opérations puis un ou plusieurs entretiens. Pour un entretien déjà codé, la validation conserve une copie de consultation : ses passages, codes et ancrages restent attachés au texte de référence. Le lecteur d’export distingue les versions.
- Dans **Personnes → Importer**, choisissez un **Excel .xlsx/.xlsm ou un CSV**. Pour Excel, choisissez la feuille et associez ses colonnes aux champs ; les colonnes Prénom et Nom peuvent être réunies. Les formules ne sont pas recalculées, les macros et liens externes ne sont pas exécutés. Préférez une copie du fichier limitée aux données utiles.
- La colonne **Entretiens liés** peut contenir un identifiant d’entretien existant (ex. `ECO-42`), plusieurs séparés par `;`, ou `INT-01:interviewer` pour préciser le rôle. Cliquez **Vérifier** puis **Appliquer** : l’import du registre et des liens se fait en une transaction. Un identifiant d’entretien inconnu doit être corrigé ; il n’est pas deviné. Les liens sont aussi modifiables dans **Bibliothèque → fiche de l’entretien → Personnes**.
- Dans **Export correcteurs**, choisissez **Copie anonymisée** ou **Copie identifiée · accès par mot de passe**. Cette dernière peut inclure les noms des intervenants, leurs liens et les transcriptions originales, sélectionnés dans l’arbre. Les copies originales conservées et les versions préparées sont des catégories distinctes. Vérifiez chaque champ utile avant de générer.
- Les deux versions sont chiffrées et exigent un mot de passe d’au moins 16 caractères. Transmettez ce mot de passe séparément du lien ou du QR. La base privée, les secrets et la table des correspondances ne sont pas ajoutés automatiquement. L’outil prépare le dossier local ; l’hébergement et les droits des destinataires restent à organiser.

### Faire relire son entretien à l’intervenant

Dans l’entretien, utilisez **Export pour l’intervenant…**. Le Word reprend la transcription originale puis la traduction si elle a été acceptée. Choisissez d’ajouter les codes et passages, les thèmes liés et les commentaires de cet entretien. Les extraits codés sont présentés dans une section distincte : leur texte de référence peut avoir été corrigé. Le document invite l’intervenant à préciser les corrections par identifiant de tour et distingue fidélité des propos, traduction et interprétation du chercheur. Relisez-le avant transmission ; rien n’est envoyé automatiquement, aucun autre entretien n’est ajouté et la génération ne vaut pas validation. Enregistrez ensuite les retours et leurs décisions dans le projet, en conservant les versions et en examinant les passages affectés.

### Validation par étapes

- Validez d’abord l’anonymisation : chaque différence peut être acceptée ou refusée. Signalez un passage oublié ou incorrect dans son champ de consigne, puis relancez la proposition et vérifiez les nouvelles différences. Une correction manuelle reste possible.
- Après validation de l’anonymisation, lancez le nettoyage et la traduction ensemble si souhaité. Décidez à nouveau chaque différence, corrigez ou relancez les passages concernés, puis validez cette étape.
- Les validations intermédiaires conservent un brouillon privé. La version finale n’est appliquée qu’après validation de toutes les étapes demandées. Les entretiens déjà codés conservent leurs passages et leur codage ; la version préparée sert de copie de lecture et d’export.

**Préparation d’un lot.** Depuis la bibliothèque, utilisez « Anonymiser / nettoyer / traduire… », puis sélectionnez les entretiens (ou « Tout sélectionner »). Le logiciel prépare toutes les anonymisations avant d’ouvrir la revue des résultats. Choisissez ensuite un entretien dans les onglets : vos décisions restent conservées lorsque vous passez à un autre résultat. Aucun résultat n’est validé automatiquement. Si un entretien échoue, les autres continuent ; « Reprendre les entretiens non traités » ne relance que les résultats manquants. Le nettoyage et la traduction d’un entretien restent conditionnés à la validation de son anonymisation.

**Serveur protégé.** Dans les réglages du modèle local, renseignez l’URL et le champ « Jeton Bearer ». Le préfixe « Bearer » est facultatif. Le jeton sert aux propositions et à la liste des modèles. Il reste uniquement en mémoire pour cette session et doit être ressaisi après redémarrage ; il ne figure pas dans la base ni dans les exports.

Le serveur peut être désigné par son nom DNS, par exemple `https://ia.cluster.example.org/v1`, avec son jeton Bearer. Les noms DNS et toutes les adresses IP sont acceptés, sans restriction au réseau privé.

### Préparation par prompt et réponse collée

- Dans « Anonymiser / nettoyer / traduire… », choisissez « Prompt à copier et réponse à coller » (mode proposé par défaut), puis les opérations et les entretiens.
- Cliquez sur « Générer les prompts ». Chaque prompt contient l’entretien complet. Copiez-le dans votre outil IA, puis collez sa réponse JSON dans le champ de l’entretien correspondant. Coding Studio n’appelle aucun modèle dans ce mode.
- Cliquez sur « Afficher tous les résultats ». Vérifiez les différences et validez l’anonymisation. Une réponse invalide peut être corrigée puis recollée.
- Pour le nettoyage et la traduction, générez ensuite le prompt correspondant, collez la réponse et vérifiez les différences avant validation. Pour signaler un oubli, utilisez les indications par segment puis régénérez le prompt.
- Les prompts et réponses sont conservés dans les données privées de préparation. Le fichier original et le codage restent inchangés jusqu’à la validation finale.

**Réponses longues en connexion directe.** Le budget de sortie initial est réglable (32768 tokens par défaut). Il est adapté au contexte disponible, indépendamment du nombre de tours. En cas de troncature signalée par le serveur, Coding Studio réessaie jusqu’à deux fois avec un budget supérieur, sans dépasser le contexte estimé. Une réponse toujours tronquée est refusée avec un message invitant à ajuster le serveur ou son thinking ; aucun extrait partiel n’est appliqué.
