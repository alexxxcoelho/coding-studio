# Coding an interview {#coder}

## Why this stage {#coder-pourquoi}

Coding means giving each useful passage a label that says what it contains. Saldaña distinguishes a first cycle of coding, descriptive and close to the respondent's words, from later cycles that group and reword. Coding Studio follows that order: you first attach concrete codes, sometimes long ones ("Staff training judged heavier than the equipment"), then you group them, and themes only emerge in the Analyse stage. The approach is hybrid in the sense of Fereday and Muir-Cochrane (2006): you may start from a palette taken from the literature, while remaining free to create codes from the data. Braun and Clarke (2006, 2021) remind us that familiarisation comes before coding, hence the memo that opens this stage.

## What you do {#coder-actions}

### 1. Write the familiarisation memo {#coder-memo}

Before coding, read the whole interview, then answer the questions of the memo template, one page at most. For the first three interviews, this memo comes before any coding: it fixes your first understanding of the case before the codes divide it up.

**In Coding Studio.** In the Library, double-click the interview, or click "Code" (Coder) in its record. On the first visit, the "Familiarisation memo" (Mémo de familiarisation) panel opens first, before any coding. The template is shown as "Default" (Par défaut). The panel displays the questions of the template chosen in the record: with the generic template, what does the respondent tell us, what surprised me, which contradictions. Each answer is a text field saved with its date. The "+ question for this interview" (+ question pour cet entretien) button adds a question (for example "Who decides what?"); you can also reword or remove a question. These changes apply to this interview only. The template itself is edited in "Settings" (Réglages). Switching template moves to another template of the study. The memo blocks nothing: you can code without having filled it in.

### 2. Go through the turns {#coder-parcourir}

The interview is split into speaking turns. The turn is the container and the navigation unit. The passage you select within a turn is the coding unit.

**In Coding Studio.** The "Coding" (Coder) screen shows on the left the "Transcript" (Transcription): a list of numbered turns (U041, U042, ...) with speaker and time marker. Interviewer turns are in grey: they give context, are not coded, and are never sent to a model. The selected turn is marked with a line on the left and stays visible when the list scrolls. The down arrow moves to the next turn, the up arrow to the previous one. The counter in the step bar (for example 40 of 61) breaks down into coded, not relevant, to review, and not yet examined units. In the left margin, coding bands show one dot per code attached to each turn. Panels are resized with the central handle.

### 3. Code a passage {#coder-passage}

By default, every respondent turn is considered relevant. A code attached without a selection covers the whole turn: this is the normal gesture. You select a precise passage when one turn carries several ideas.

**In Coding Studio.** On the right, the "Codes" panel lists the codes with their name and a short definition, with sub-codes indented below. The first nine have a number: press 1 to 9, or click. To code a precise passage, first select the text with the mouse, then choose the code. Enter validates, and the down arrow moves to the next turn. The code appears as a dot under the turn header. When the list has more than nine codes, the slash key opens keyboard search: typing filters the list, and Enter attaches the first match. For a turn of no interest (politeness, logistics, digression), press N: it is marked NA, counted as not relevant, and leaves the rest of the process. For a turn that leaves you in doubt, press R: it is marked "to review".

### 4. Attach several codes to a passage {#coder-multicodes}

The same passage can relate to several phenomena. Attach several codes if, and only if, they describe distinct things.

**In Coding Studio.** Attach a first code, then a second one to the same turn or passage: both dots appear. Fictional example: "Six months for the first two annexes, mainly because of training the volunteers; the equipment, by contrast, was ready in three weeks." The first passage carries "Staff training judged heavier than the equipment", the second "Equipment available quickly", each with its own underline. An added code never overwrites another, and a removed code stays in the history.

### 5. Create a code on the fly {#coder-nouveau-code}

When no code fits and the passage matters, you create a code on the spot. This is how the codebook is built.

**In Coding Studio.** At the bottom of the Codes panel, click "New code" (Nouveau code) from this unit. A small form opens in place: a name in everyday words, a one-sentence definition saying what the code includes and excludes, and an optional parent. Confirm: the code is created, attached to the current unit, and this unit becomes its origin and its first example. The codebook version moves up one step. Each code receives a stable identifier that does not change if you rename it. Prefer names that say what the respondent says and the judgement they make ("Equipment investment judged disproportionate for a small organisation") over vague words ("Costs").

### 6. Use the "Later" (Plus tard) code {#coder-plus-tard}

If you hesitate over an important passage, do not force a code: attach "Later".

**In Coding Studio.** "Later" (identifier LATER) is a system code that always appears in the list. Attach it like any other code, with a note if you wish. The Codebook shows the number of units concerned (for example 7 units to review). When a new code appears, the tool lists the units from earlier interviews that carry its parent or "Later", so that you can review them. See action 7.

### 7. Organise the code tree {#coder-codebook}

Codes form a tree of three levels that follows the progress of the analysis: descriptive codes, focused codes that group them (the parent), then, later and elsewhere, themes. Placing a code under a parent changes no coding; merging two codes recodes all their units. These two gestures are different.

**In Coding Studio.** Click "Codebook" in the top bar. For each code, the tree shows its name, its origin (literature or field), the questions it serves and its number of passages. Drag a code onto another to make it a sub-code; a code attached to a sub-code also counts for its parent in the exports. Click a code to open its record: name, definition (includes, excludes), parent, questions concerned, origin, example. "Merge into..." (Fusionner dans...) recodes all units to another code while keeping a trace of the old one. "Disable" (Désactiver) hides a code without touching past codings. Every move is dated and justified, and the codebook version changes with each modification. "Import CSV" (Importer CSV) loads a starting palette, which is not an established truth. Every three interviews, re-read the list to merge synonyms and split codes that are too broad. When a code appears midway through, the record lists the units from earlier interviews to review.

### 8. Keep a code memo {#coder-memo-code}

A code evolves. The code memo keeps the reason for its changes.

**In Coding Studio.** In a code's record, the "Code memo" (Mémo du code) area receives dated entries: why the code exists, your hesitations, the merges. The "See the passages carrying this code" (Voir les passages qui portent ce code) link opens them with their interview and context: read them in one go before merging.

### 9. Highlight without coding {#coder-surlignages}

A highlight keeps a passage without coding it yet. It is used to build codes from the first interviews.

**In Coding Studio.** On the Coding screen, select a passage with the mouse then press H, or click "Highlight" (Surligner). The passage is highlighted without a code. The "New code from highlight" (Nouveau code depuis le surlignage) button creates a code for which the passage becomes the example and the origin. A highlight is not a code. It stays visible after coding and can serve as a candidate quotation. The information panel shows the number of highlights without a code (for example 5).

### 10. Use the "Lexicon" (Lexique) {#coder-lexique}

The Lexicon proposes code names from the words of your highlights. It judges nothing and uses no generative AI.

**In Coding Studio.** Select a highlight: the "Lexicon" panel shows its keywords (statistical extraction, deterministic, in three languages) and their roots. Using these words as a provisional label pre-fills a code name. The "Keywords" (Mots-clés) list across all highlights gives, for each word, the number of passages and the interviews concerned: tick words to see the passages that carry them, then click "Create a code from this selection" (Créer un code à partir de cette sélection). The "Nearby passages" (Passages proches) panel lists passages from other interviews that share the vocabulary of the highlight, with a similarity score. It helps you check the coverage of a code and find what you may have missed. Limit: the lexicon cannot see synonyms or different languages.

### 11. Go through the end-of-interview checklist {#coder-checklist}

The checklist is a final check before you consider the interview coded.

**In Coding Studio.** When the respondent's last turn is coded, the "End of interview" (Fin d'entretien) panel opens (study checklist). Its points are those set in Settings (see [Prepare](01_prepare.md#preparer-checklist)); by default: all the respondent's turns seen; "Later" codes handled or accepted; memos written for the new codes; end-of-interview memo written. The last point has a note area: this is where you write the respondent's position, the central mechanism, the exceptions and the questions for the following interviews. It is separate from the familiarisation memo. To check the uncoded segments, also re-read the turns next to the coded passages. The checklist is never a lock.

### 12. Prepare a quotation: the "Detail" (Détail) drawer {#coder-detail}

When you decide to quote a unit, and only then, you prepare it in the Detail drawer. For the units you do not quote, nothing that follows is required.

**In Coding Studio.** On the Coding screen, the "Detail" button of a turn (quotation, audio, flags), or a click on a passage in "Write", opens the drawer on the right of the transcript; it is closed by default. It has three blocks.

A. Check against the audio. An indicator shows the status: unverified, verified or unusable. Click "Open audio at 12:10" (Ouvrir l'audio à 12:10), the marker of the unit, and listen again. Click "Mark verified" (Marquer vérifié) or "Unusable" (Inutilisable). The "Correct text or speaker" (Corriger le texte ou le locuteur) button saves the correction with its date and reason; the original remains readable and the unit goes back to unverified.

B. Quotation. Select with the mouse the exact passage to quote; the tool checks that it is an exact substring of the turn. Qualify it with three menus. The "Nature of evidence" (Nature de la preuve) describes the statement: first-hand account, reported speech, quantified estimate, cited document, opinion. These types describe; they do not rank: a quantified estimate is no more reliable than a direct account. The "Origin" (Origine) says how the statement came about: spontaneous, prompted by my question, taken from a document, or inferred by me. The "Role" (Rôle) says what the statement does in the decision: trigger, after-the-fact justification, enabling condition, constraint, or undetermined. The codes supported by the quotation are displayed. Click "Save quotation" (Enregistrer la citation). For the units you do not quote, none of this is required; your reports show the share of verified units. Quotations already saved on the unit are listed.

C. Flags (optional). Four boxes: uncertain attribution or word, reported speech, unfinished sentence, agreement with your wording. The last one asks whether it is a simple yes or an answer with its own content. Nothing else.

The list of evidence types can be edited in Settings, with these default values.

## Common pitfalls {#coder-pieges}

- Coding the interviewer. Their turns are in grey: they shed light on the answer, they are not coded.
- Turning an inference into a fact. If the respondent speaks of a lack of economic interest, do not code a lack of skills.
- Confusing placing under a parent with merging. The first action changes no coding, the second does.

## What this stage delivers {#coder-sortie}

- An interview in which every respondent turn has been examined: coded, not relevant, to review, or Later.
- Precise passages, with their exact position, carrying one or several codes.
- A codebook that grows, with definitions, a version and dated code memos.
- A familiarisation memo and an end-of-interview memo.
- A checked checklist, and highlights usable as examples.
